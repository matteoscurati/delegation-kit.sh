# Getting started

delegation-kit installs, on one machine, everything Claude Code and Codex need
to delegate bounded coding work to the models you choose: a personal
configuration, the read-only router, one dispatcher for every adapter, the six
provider runners with their own sandboxes, host profiles, skills, and the
always-loaded user-direction guard. It never dispatches on its own.

## Requirements

macOS, `jq`, `git`, `python3`. Claude Code and/or Codex for the native
adapters. Provider runners need their own credentials: the installer asks once,
stores keys mode 600, and never copies them silently from another tool.

## Install

The shortest path is the npm installer. It clones the tagged release, verifies
it, and runs the same `install.sh` a clone would; nothing is copied into
`node_modules`:

```sh
npx delegation-kit           # interactive: asks for external keys once
npx delegation-kit --claude-only
npx delegation-kit --codex-only
npx delegation-kit --skip-doctor
```

From a clone, which is also where `doctor.sh` compares the installed kit with
the sources:

```sh
git clone https://github.com/matteoscurati/delegation-kit
cd delegation-kit
./install.sh        # or --claude-only / --codex-only
./doctor.sh         # verify everything is wired (add --ping for a live round-trip)
```

Claude-only, from the plugin marketplace:

```
/plugin marketplace add matteoscurati/delegation-kit
/plugin install delegation-kit
```

`./uninstall.sh` (or `npx delegation-kit --uninstall`) removes every installed
file, link, and guarded block, and preserves stored keys as mode-600 backups.

## What the installer sets up

- **A personal configuration** at
  `${XDG_CONFIG_HOME:-$HOME/.config}/delegation-kit/config.json` (override with
  `DELEGATION_CONFIG_FILE`). A fresh install gets the default preset: one
  profile per model the kit knows, review `optional`. An existing file is never
  overwritten; a legacy install is snapshotted as `migration-v1-backup` first.
- **Managed host snippets** under `managed/` next to it, regenerated by
  `delegation-config apply` and preserved once you edit them.
- **Commands** on `~/.local/bin`: `delegation-config`, `delegation-route`,
  `delegation-run`, `delegation-openai-compatible`, the six provider runners,
  and `delegation-patch-verify`.

`./doctor.sh` has a "Personal configuration" section that answers "is this
machine wired": configuration valid, review policy, managed snippets present,
the commands on PATH, and the builder role resolving selectable profiles.

## Your first delegation

Delegation is user-directed and per dispatch. The flow is always the same:

```sh
# 1. Configure — inspect or edit your profiles; validate without touching a provider
delegation-config show
delegation-config validate

# 2. Resolve — read-only, never dispatches
delegation-route resolve --lane builder --json
#    → {"choices": [...], "blocked": [...], "authorization_granted": false}

# 3. You choose — name the profile, or authorize the lead to pick from .choices
#    "Use terra-builder for <task>."
delegation-route resolve --lane builder --selected-profile terra-builder --json

# 4. Run — only now, once
delegation-run --profile terra-builder --lane builder \
  --prompt-file /tmp/task.txt --output /tmp/result.txt --workdir /path/to/repo
```

`delegation-run` writes the output, a metrics file, and `result.txt.result.json`:
requested versus provider-reported model, `review_status`, and
`status: ready-for-integration` or `pending-review`. Output paths must be new
and outside the worktree. Text adapters return a patch; the lead applies and
tests it. Retries and reviews are dispatches too: each needs its own approval
unless your request named that finite set.

## Roles and adapters

A profile lists the roles it may take: `clerk`, `scout`, `builder`,
`frontend-builder`, `reviewer`, `routine-review`, `material-review`,
`security`, `senior`, `judgement`, `policy-annotation`. The **adapter** decides
what a role can actually do: text adapters (`deepseek-api`,
`token-plan-openai`, `openai-compatible`) only send the prompt and return text
or a patch; native adapters (`kimi-code-cli`, `claude-zai`, `grok-build-cli`,
`codex`, `claude-code`) keep their own sandboxes and file-access controls.
Assigning `builder` to a text adapter cannot grant worktree access. The full
matrix, with what each adapter supports today, is on the [home page](/).

## Review

`review_policy` in your configuration is `optional` by default. `required`
accepts any compatible reviewer; `cross-family` requires the reviewer's
declared family to differ from the producer's. A mandatory policy never
authorizes the reviewer call: the result stays `pending-review` until the lead
obtains and verifies that review. `delegation-config init --preset strict`
selects `cross-family` for a new configuration.
